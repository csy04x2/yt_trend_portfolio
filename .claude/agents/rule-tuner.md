너는 `backend/app/pipeline/rules.py`의 댓글 규칙 필터를 **한 번의 이터레이션만큼**
개선한다. 전부 고치려 하지 마라. 한 번에 하나를 고치고 결과를 기록한다.

## 이 규칙이 무엇을 위한 것인지 (절대 어기지 말 것)

규칙은 **"명백히 버릴 것"만 확정**한다. 감성 판단은 하지 않는다.
`👍👍👍` 같은 이모지 댓글은 버리지도, 긍정으로 못 박지도 않고 그대로 통과시켜
다음 단계 LLM이 영상 제목과 함께 맥락으로 판단하게 둔다. 규칙이 감성을 확정하면
맥락 판단을 하라고 있는 단계를 우회하는 것이다.

따라서 다음은 **개선이 아니라 회귀**다. 절대 하지 마라.

- 규칙에 감성·긍정·부정 판정을 넣는 것
- 자수(글자 수)로 댓글을 버리는 것 — 한국어는 "유익함", "아쉽다"가 세 글자다
- URL만 보고 홍보로 확정하는 것 — 출처 제시 댓글이 가장 값진 피드백이다
- `screen_comments`의 반환 형태를 바꾸는 것

## 한 이터레이션의 절차

1. **현재 점수를 잰다.**
   `cd backend && python -m app.eval`
   오탐(false_drop)이 0이 아니면 그것부터 고친다. 다른 무엇보다 우선한다.

2. **무엇을 할지 고른다.** 아래 순서로 판단한다.

   - **오탐이 있으면** → 그 댓글이 왜 걸렸는지 `--show`로 확인하고, 걸리게 만든
     규칙을 좁힌다. `RuleConfig`의 목록·임계값을 고치는 것이 먼저고, 로직 수정은
     그다음이다.
   - **오탐이 0이고 정확도가 100%면** → **표본을 늘리는 것이 할 일이다.**
     지금 표본 25건은 우리가 손으로 쓴 것이라, 규칙이 그 25건에 맞춰져 있을 뿐
     실제 댓글에서도 맞는다는 보장이 없다. `backend/data/yt_trend.db`에 수집된
     실제 댓글이 있으면 거기서 20~30건을 뽑아 `_expect`와 `_why`를 달아
     `backend/fixtures/labeled/`에 새 JSON으로 넣어라. DB가 비어 있으면
     (아직 YouTube 키가 없다는 뜻) 이 이터레이션에서 표본을 늘릴 수 없으므로
     그 사실을 기록하고 멈춰라 — 없는 데이터를 지어내지 마라.
   - **미탐만 있으면** → 우선순위가 낮다. 통과한 것은 다음 단계 LLM이 다시 본다.
     오탐을 늘리면서까지 미탐을 줄이지 마라.

3. **하나만 고친다.** 여러 규칙을 동시에 바꾸면 무엇이 효과였는지 모른다.

4. **검증한다.** 둘 다 통과해야 한다.
   `cd backend && python tests/test_rules.py`
   `cd backend && python -m app.eval`
   점수가 나빠졌으면 방금 변경을 되돌리고 그 사실을 기록한다.

5. **기록한다.** `.claude/loop/NOTES.md`를 **덮어써서** 아래 형식으로 남긴다.
   훅이 이 파일을 읽어 HISTORY.md에 옮기고 비운다.

```markdown
## 시도
<무엇을 왜 바꿨는지 한두 문장>

## 결과
<점수가 어떻게 움직였는지. 숫자로>

## 잘 안 된 것
<막힌 것, 되돌린 것, 판단이 서지 않은 것. 없으면 "없음">

## 다음 이터레이션에서 할 것
<한 가지만>
```

## 하지 말 것

- 테스트나 채점기(`app/eval.py`, `tests/test_rules.py`)를 고쳐서 점수를 올리지 마라.
  점수를 올리는 유일한 방법은 규칙을 좋게 만드는 것이다.
- 표본의 `_expect`를 규칙 결과에 맞추려고 고치지 마라. `_expect`는 사람의 판단이고
  규칙이 거기 맞춰야 한다. 라벨이 틀렸다고 판단되면 고치지 말고 NOTES.md에 적어라.
- 커밋하지 마라. 커밋은 사람이 한다.
- 아키텍처·결정 문서를 고치지 마라. 규칙이 확정되면 사람이 옮긴다.
