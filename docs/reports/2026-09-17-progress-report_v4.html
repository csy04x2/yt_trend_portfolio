영상 특징 — 일시 정지

09-17 결정으로 반응 분류 뒤로 밀렸다. 그 전까지의 진척과 막힌 이유를 남긴다.

09-14에 사람이 전부 라벨하는 대신 자동 추출기 + 사람 검토로 방향을 바꿨다. 첫 기준 특징인 게스트 출연은 제목·설명만으로 판정한 것은 모두 맞았지만, 사람이 찾은 게스트 중 39%만 잡았고 쇼츠는 거의 판정하지 못했다. 09-15에는 추출 단계 구조, Finding Engine, 판정·동결 절차가 코드로 들어갔다.

같은 날 점검 기록은 이 트랙을 막힘(BLOCKED)으로 판정했다. 승인된 사람 특징 목록이 없고, 저장소의 특징 12개는 후보이며 90편 × 12개 판정은 제목 정규식 자리표시자라는 이유다. 09-17에는 특징을 세 층으로 나눈 구조가 확정됐다.

저장소와 이 PC의 파일을 읽기만 해서 확인했다.

1. 원천 자료가 두 PC에 나뉘어 있고, 어느 쪽도 전체를 갖고 있지 않다

2. 정본이 main에 없다

정본 문서 여섯 개와 새 README가 전부 integration 브랜치에만 있다. main의 README는 여전히 옛 문서표이고, main을 보는 사람은 R1~R8을 현행 체계로 읽게 된다. integration은 main의 후손이라 빨리감기로 충돌 없이 합쳐진다.

main 밖 커밋: integration 15 · feature-discovery-experiment 8 · offline-comment-labeling 2 (중복 제외 24)

3. Gemini 감사 프롬프트는 쓸 수 없다

프롬프트는 09:39에 쓰였고, 한 시간 뒤 정본이 확정됐다. 프롬프트는 R1~R8을 침착맨에 시험하자는 내용인데 체계는 10+5로 바뀌었고 침착맨은 Phase 2에서 제외됐다. 프롬프트가 묻던 정의 위치·원천·중복 여부는 데이터 장부가 이미 대부분 답하고 있다.

4. 특징 12개를 두 문서가 다르게 말한다

09-14 인수인계는 "특징 12개 동결"이라고 적었고, 09-15 점검 기록은 "승인된 사람 특징 목록이 없다, 현재 12개는 후보"라고 적었다. README가 점검 기록을 정본으로 지정했으므로 뒤의 것이 맞다. 저장소에 있는 12개는 Claude 재현본이다.

5. 결론 문장 만들기가 새 단계 경계를 넘는다

09-17 경계는 "08단계까지는 사실과 관계만 계산하고, 해석은 09단계에서만 한다"이다. 그런데 main의 aggregate.py는 08단계에서 가장 높은·낮은 유형을 골라 결론 문장 초안을 쓰고 Claude로 다듬는다. 정본 문서도 이 설명을 "과거 설계, 현재 허용 범위 아님"으로 못박았다. 이 기능은 09단계로 옮겨야 한다.

6. 작은 것

영상 다운로드(특징 Stage 2)는 약관 확인이 아직 미결이지만, 특징 작업이 멈춰 급하지 않다. 침착맨 특징 재현 README가 언급하는 discovery90-labels.json은 커밋에 없다.

06
보류 — 영상 특징·성과 지표의 재개 조건

승인된 사람 특징 목록(14F 사람 판정 포함), 별도 고정 기준 영상 집합, 영상 다운로드 약관 판단, 결론 문장 기능의 09단계 이전. 이 조건이 갖춰지기 전에는 최종 Finding과 봉인 분할 검증을 실행하지 않는다.

2026-09-17에 원격 브랜치 전부를 가져와 읽기만 해서 확인했다. 커밋과 브랜치 차이는 git log·git rev-list, 병합 가능성은 git merge-base로 봤다. 정본 수치와 결정은 integration 브랜치의 문서(Reaction Phase 1 Checkpoint, 데이터 장부, Control Tower 점검 기록, 두 준비도 점검, Content Feature Structure, 아키텍처 현재 경계)에서 옮겼다. 원천 자료 대조는 이 PC의 SQLite DB 네 개를 읽기 전용으로 열어, 장부가 가리키는 저장소 파일의 댓글 ID와 비교했다. 장부에 적힌 작업 폴더의 존재 여부는 이 PC에서만 확인했으므로 다른 PC의 상태는 확인하지 않았다.
